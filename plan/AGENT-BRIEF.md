# Briefing an agent on a ticket

A delegate reads `CLAUDE.md` on its own. A brief names the ticket and what is specific to it, and leaves out what this file and `CLAUDE.md` already say.

## Rules for every agent

- Never use the fable model, and never spawn a subagent on it. Use opus for the hardest work.
- Before building, list what `origin/master` already has for the ticket: its commits (`git log origin/master --grep '#N\b'`), its endpoints in `server/legacy_api/registry.py`, and the handlers and services that exist. Build what the list lacks, and put the list in the final report.
- Work in its own git worktree, on a branch named `issue-<n>-<slug>`. Check `git branch --show-current` before any pull or merge in the main clone, because other sessions use it.
- Commit with `git -c user.name=PorkChopExpress86 -c user.email=<owner email> commit`, and end each message with the `Co-Authored-By` line the session gives. Push the branch, and leave the PR and the merge to the lead.
- Edit no issue body and no owner decision. Put proposed ticks in the final report.
- Send the lead each question only the owner can answer as soon as you find it, then build around it. #54 found its token question early and reported it after the whole ballot was built. `plan/bin/ci-suites N` also lists the parity-gate entries that name the ticket, a question to raise at the start.
- Before building, check each number, range and choice in the ticket's acceptance boxes against the PHP source, and send a mismatch to the lead then. #48's ticket said a fake roster "sees 30" where PHP adds -2 to +2 racers to each group at random (`action.racer.fake.inc:31-35`, C57), and its setting ranges came from the ticket instead of `settings.php`'s inputs; the review found both.

## Django handlers

- A handler under `server/legacy_api/handlers/` is a thin adapter. It parses `ctx.args`, calls a service, and encodes the result. The guard in `server/legacy_api/tests/test_registry.py` fails a handler that writes through the ORM.
- A service that changes roster, inspection, lane, or result data takes `core.services.lock_race_state(event_id)` first inside `transaction.atomic()`. A handler or a `ui` view never reads race state before a service call and acts on it after: the service reads it again under the lock. A read the change must match, such as #48's snapshot before a purge, is taken under that lock too: taken before it, a racer added in between was purged unrecorded. `server/ui/tests/test_read_then_act.py` flags a view that refuses on what it read, or answers with a row it read and never handed to the service; build the toast and the Undo from what the service returns.
- One user action is one service call, so all its writes commit or roll back together. #42's review found a racer saved in one transaction and its award settings in a second.
- A ported action refuses in PHP's order: one test sets every refusal condition at once and expects PHP's first code. A row it creates sets every column PHP's INSERT sets. #54's `vote.cast` asked for the password before PHP's closed check, and its Voters row left out `when_cast` and `ip_addr`.
- A record that must survive a refusal is written after the atomic block, because the rollback removes it.
- A service that changes a setting decides what happens to each stored row the setting governs, and a test changes the setting with such rows present. When PHP and the owner decisions leave it open, ask through the lead. #70's review found a stored weigh-in pass kept after the partition's maximum changed, and a Failed weigh-in kept after the mode changed.
- Every endpoint needs a `LEAK_REQUESTS` entry in `server/legacy_api/tests/test_event_leak.py`.
- A deliberate difference from PHP goes in the endpoint's `divergences` in the registry, citing a quirk id or an owner decision (`D48`). A difference that a recorded golden fixture shows also goes in `server/tests/golden/deviations.json` (D25).
- Each parity-gate allowance (a `ParityPath` in `PARITY_PATHS` or `STEP_PATHS`, a contact window) gets a test beside it where a difference just outside its decision still fails: another role, another scene, a contact after the window. #218's review found D16 allowed for every caller, D5 for logged-in callers, D10 for every scene, and a window with no end when no later poll came.
- A new Django-only endpoint is added to `DJANGO_ONLY` in `server/legacy_api/tests/test_registry.py`. A new event-scoped model needs a row in `server/core/tests/populated.py`. Run `pytest core/tests legacy_api/tests/test_registry.py legacy_api/tests/test_event_leak.py` before the full suite, because these fail only there otherwise.
- Replay suites hold PHP's state after each script step: `roster/tests/test_group_scenarios.py`, `legacy_api/tests/test_groups_parity.py`, `racing/tests/test_round_scenarios.py`, `racing/tests/test_finalists.py`. Run them before changing a behavior they cover. A fix they break needs a narrower condition or a recorded deviation, never an edited expectation.

## UI pages

- htmx inheritance is off (`server/ui/templates/ui/base.html`), so each element that makes a request names its own `hx-target`, `hx-swap`, `hx-sync` and `hx-include`. `server/ui/tests/test_htmx.py` checks the page-wide htmx rules.
- A value the page sends back to the server, such as an Undo link's query or a hidden field, is client input. The service checks it as it checks a new request, and the same request sent twice changes nothing the second time. #44's Undo stored a forged `runs=0` and restored a step twice. `hx-sync="...:drop"` drops a request only while another is in flight, so a repeat sent after the reply needs a service-side guard, such as #49's import token. `server/ui/tests/test_undo_links.py` replays and alters each Undo link a view offers; a new Undo adds its scenario there. A list the page keeps and posts back whole, such as #54's chosen cars, gets a test that makes one item invalid between load and post: #54's vote page kept a car the award could no longer take, and every later vote failed.
- A page that differs from the PHP page it replaces cites a quirk id or an owner decision (`D69`) at the difference, in the code and in any README that describes it, as an endpoint's `divergences` do. #49 and #50 each shipped five such differences with no id until review. `server/ui/tests/test_navigation.py` fails a newly built page until its PHP page is in `ROUTE_DIVERGENCES`, `UNDECIDED_DIVERGENCES` (no id yet; the PR's `## Still open` names each) or `LIKE_PHP` (`server/legacy_api/registry.py`). A difference the ticket's scope asks for is a question for the owner through the lead before the PR, not an `UNDECIDED_DIVERGENCES` entry: #54 parked two there that became D77.
- Each rule lives in its service, and a view or a page's `state.py` calls it. `server/ui/tests/test_rules_in_services.py` flags a lane mask or a service limit copied into one, or a literal bound in its template.
- `server/ui/tests/test_query_growth.py` reads each page, poll and hx-get fragment at two sizes of race day and fails when the query count grows; its first test names a fetched URL missing from `URLS`. Its `race_day()` also feeds `test_poll_signatures.py`, so a feature that adds stored state adds rows in that state there, or both checks pass without rendering it. #70's review found race day with no weigh-in.
- A new page checks its PHP page's `<script src>` tags: `server/ui/tests/test_php_libraries.py` fails a third-party library the port neither serves nor records as replaced. #52's `fullscreen.php` left out `screenfull.min.js`.
- A setting's bounds and choices are PHP's markup: `server/ui/tests/test_settings_bounds.py` reads them from `settings.php` and `coordinator.php`. A new page with number inputs or `<select>` choices gets the same check.
- `server/tools/source-checks.sh` runs the tests that read only the source (PHP cites and claims, `QUIRK_DECISIONS` records, copied helpers, rules in services, read-then-act, the registry) in seconds, and the pre-push hook runs it. Run it after each batch of edits: #48 found five of them failing one round at a time.
- The page-wide checks fail a new page only once it is registered and renders: `pytest -n auto ui/tests/test_navigation.py ui/tests/test_every_view.py ui/tests/test_query_growth.py ui/tests/test_photo_urls.py` takes about 3 minutes, against 10 per database for the full suite. Run it as soon as the page has its URL and its registry entry. #52's full suite found four such failures, one round at a time.
- A poll that answers 204 signs everything it renders. `server/ui/tests/test_poll_signatures.py` changes each stored field in turn and fails a poll that still answers 204 when its rendering changed. #45's presenter signed the award's key and winner, not the names it shows.

## Evidence

- A claim counts once a test or a real server run reproduces it. That covers a sentence in `GLOSSARY.md`, `plan/owner-decisions.md` or a docstring that says what the server does. Name the test or the code that shows it.
- A comment saying the port does what a PHP page does is a claim too: check it against PHP with `testing/docker/php-scratch.sh`. #44's playlist back button said "as playlist.php does" and was wrong until #46's retro. Cite the PHP file and line (`kiosks.inc:27-31`) or the test beside the comment; #50's and #52's reviews each sent back comments with neither; `server/tests/test_php_claims.py` now fails an "as X does" with neither. The PHP files `.gitignore` lists under `website/` are built from `templates/` by `build.xml`, so `make_banner()` is in `templates/banner.inc`.
- Run the shell suites in `testing/` against a live Django server the way `.github/workflows/server.yml` does. Add a suite to that workflow once it passes on SQLite and Postgres with no stand-in. `plan/bin/ci-suites N` lists the suites ticket N names that the workflow lacks; the PR body names the ticket each one waits on.
- Run the affected tests on Postgres (`server/tools/pytest-postgres.sh`) each time you run them on SQLite, not after SQLite is green. #49 found jsonb's sorted keys after its SQLite runs passed and spent its longest stretch there.
- Run the full server suite once at the end, in the background, and read its exit code before pushing. Run it alone: beside a `tools/pytest-under-load.sh` run, #54's full suite failed tests that pass alone.
- Golden captures from PHP need a regular clone, not a worktree. Ask the lead to run `server/tests/golden/capture.sh`, narrowed with `GOLDEN_SCENARIOS`.
- Before the PR, merge `origin/master` into the branch and rerun the affected tests.
