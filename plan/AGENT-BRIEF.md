# Briefing an agent on a ticket

A delegate reads `CLAUDE.md` on its own. A brief names the ticket and what is specific to it, and leaves out what this file and `CLAUDE.md` already say.

## Rules for every agent

- Never use the fable model, and never spawn a subagent on it. Use opus for the hardest work.
- Before building, list what `origin/master` already has for the ticket: its commits (`git log origin/master --grep '#N\b'`), its endpoints in `server/legacy_api/registry.py`, and the handlers and services that exist. Build what the list lacks, and put the list in the final report.
- Work in its own git worktree, on a branch named `issue-<n>-<slug>`. Check `git branch --show-current` before any pull or merge in the main clone, because other sessions use it.
- Commit with `git -c user.name=PorkChopExpress86 -c user.email="$(git -C <main clone> config user.email)" commit`, which reads the owner's address from the main clone's `.git/config` instead of typing it: #307's implementer saw a command with the address typed out refused as a privacy leak. The same line works in a fresh clone with no config of its own, such as the screenshots clone. End each message with the `Co-Authored-By` line the session gives. Push the branch, and leave the PR and the merge to the lead.
- Edit no issue body and no owner decision. Put proposed ticks in the final report.
- Send the lead each question only the owner can answer as soon as you find it, then build around it. #54 found its token question early and reported it after the whole ballot was built. Each question recommends what PHP does, with its file and line, or says why not: #231 recommended dropping dead class ids to `[]`, which shows every class, though the same message said PHP shows nobody; the owner chose PHP's rule, which cost a second commit, parity run and full suite. Start the parity run and the affected tests (`plan/bin/affected-tests`, owner, 2026-11-11) on the head that answers the questions. `plan/bin/ci-suites N` also lists the parity-gate entries that name the ticket, a question to raise at the start.
- A choice between candidate rules or tools goes to the lead with what each catches that the other misses, both ways, not only the counts. #346 sent the counts of rules B and C and B's noise; the advisor then found eight verbs only B caught, review a ninth, and the lead decided twice while the findings went from 42 to 52 (#346 retro).
- A trade-off you would name in your report as part of what the user sees, such as a page that shows less than the page it stands for or less than PHP shows, is such a question: send it before building on it, even when you judge it fine. #237's thumbnails drew 6 of 15 kiosk pages emptier than the kiosk (no lineup, award, on-deck chart or QR code), which the implementer judged a fair trade-off and built on; the owner chose D84 instead, and the fix took a second round. Code, docs and the PR body cite the lead's answer by the decision it rests on and the ticket (`D10`, `#272`), since a reviewer sees no message from the lead: #272's docstring said "the lead's choice B" until review. When the owner can pick options together, walk each input the ticket names (each key, the pointer, a poll) through the combination, or run it on the stand-in page, and send each cost it shows, and the exact rule the code will match by, with the question: #369's question said a focus restore would let a held Enter's repeats post again, but not that a held Space's repeats would land on the restored button too, and it named the control's match as `data-scene` or `data-kiosk` with `data-action`, where D127 matches name, value, `data-action` and card. Both reached the owner after the build, as Q40 and Q43, and cost D131 (#384) and a second build round.
- An acceptance box you judge the code already meets as it stands, such as a "clear message" met by an existing error, is such a question too: send the lead the output you would show for it before building on it. #308 judged Django's bare `OperationalError` clear enough, said so only in the PR body, and review sent it back.
- Send the lead each gap you know of and have no test for before the push, with what you tried, so the lead or review can build the test while the branch is open. #239's implementer named a page that reloads mid-check in its report; review's stand-in page that reloads every second crashed the tool 8 of 8.
- Before building, check each number, range and choice in the ticket's acceptance boxes against the PHP source, and send a mismatch to the lead then. #48's ticket said a fake roster "sees 30" where PHP adds -2 to +2 racers to each group at random (`action.racer.fake.inc:31-35`, C57), and its setting ranges came from the ticket instead of `settings.php`'s inputs; the review found both.
- A behavior the ticket's Risks or the lead's condition states, such as "not on a timer", gets a test like an acceptance box. #250's fit() on every poll passed every test until review.
- A tool under `plan/bin`, `server/tools` or `.githooks` that acts (merges, pushes, edits an issue) after a long step reads the state it acts on again just before acting, and a test changes that state during the step. A tool that cleans up in a trap is tested with a second signal during the cleanup, and with a SIGKILL followed by its next run. Its test holds a signal at each line between starting a child and recording it, and between its `wait` and clearing that record (`paused_copy()` in `server/tests/test_pytest_under_load.py`): review found three such windows in #391. #311's pr-merge read origin/master once and merged 16 min later; the review pushed master mid-run and pr-merge merged anyway, and a second Ctrl-C or a SIGKILL left its run and worktree (#333 review).

## Django handlers

- A handler under `server/legacy_api/handlers/` is a thin adapter. It parses `ctx.args`, calls a service, and encodes the result. The guard in `server/legacy_api/tests/test_registry.py` fails a handler that writes through the ORM.
- A service that changes roster, inspection, lane, or result data takes `core.services.lock_race_state(event_id)` first inside `transaction.atomic()`. A handler or a `ui` view never reads race state before a service call and acts on it after: the service reads it again under the lock. A read the change must match, such as #48's snapshot before a purge, is taken under that lock too: taken before it, a racer added in between was purged unrecorded. `server/ui/tests/test_read_then_act.py` flags a view that refuses on what it read, or answers with a row it read and never handed to the service; build the toast and the Undo from what the service returns.
- A file found under a lock, such as a photo's render, is opened under that lock, and the view streams the open file after. #302's view took the render's path under the photo's lock and opened it after the release, where a waiting rotation's `tidy()` unlinked it; #35's race test raced by timing, so it failed only now and then under load. A race test holds each gap open with a hook at the lock's release and before the open (`media/tests/test_photo_races.py`), so it fails every run.
- One user action is one service call, so all its writes commit or roll back together. #42's review found a racer saved in one transaction and its award settings in a second.
- A ported action refuses in PHP's order: one test sets every refusal condition at once and expects PHP's first code. A row it creates sets every column PHP's INSERT sets. #54's `vote.cast` asked for the password before PHP's closed check, and its Voters row left out `when_cast` and `ip_addr`.
- A record that must survive a refusal is written after the atomic block, because the rollback removes it.
- A service that changes a setting decides what happens to each stored row the setting governs, and a test changes the setting with such rows present. When PHP and the owner decisions leave it open, ask through the lead. #70's review found a stored weigh-in pass kept after the partition's maximum changed, and a Failed weigh-in kept after the mode changed.
- Every endpoint needs a `LEAK_REQUESTS` entry in `server/legacy_api/tests/test_event_leak.py`.
- A deliberate difference from PHP goes in the endpoint's `divergences` in the registry, citing a quirk id or an owner decision (`D48`). A difference that a recorded golden fixture shows also goes in `server/tests/golden/deviations.json` (D25).
- Each parity-gate allowance (a `ParityPath` in `PARITY_PATHS` or `STEP_PATHS`, a contact window) gets a test beside it where a difference just outside its decision still fails: another role, another scene, a contact after the window. #218's review found D16 allowed for every caller, D5 for logged-in callers, D10 for every scene, and a window with no end when no later poll came. When the decision relates the two sides, such as D82's "Django keeps at least PHP's rows", one test breaks that relation (PHP 12 against Django 5); a normalizer's fallback branch gets one too (an id that names no row against a renumbered id). #221's review found both passing.
- A new Django-only endpoint is added to `DJANGO_ONLY` in `server/legacy_api/tests/test_registry.py`. A new event-scoped model needs a row in `server/core/tests/populated.py`. `plan/bin/affected-tests` maps a model or a migration to `core/tests`, `legacy_api/tests/test_registry.py` and `legacy_api/tests/test_event_leak.py`, and a handler or a service to the last two, because these fail only there otherwise and CI's full suite finds them a round late (owner, 2026-11-11).
- Replay suites hold PHP's state after each script step: `roster/tests/test_group_scenarios.py`, `legacy_api/tests/test_groups_parity.py`, `racing/tests/test_round_scenarios.py`, `racing/tests/test_finalists.py`. Run them before changing a behavior they cover. A fix they break needs a narrower condition or a recorded deviation, never an edited expectation.

## UI pages

- htmx inheritance is off (`server/ui/templates/ui/base.html`), so each element that makes a request names its own `hx-target`, `hx-swap`, `hx-sync` and `hx-include`. `server/ui/tests/test_htmx.py` checks the page-wide htmx rules.
- A value the page sends back to the server, such as an Undo link's query or a hidden field, is client input. The service checks it as it checks a new request, and the same request sent twice changes nothing the second time. #44's Undo stored a forged `runs=0` and restored a step twice. `hx-sync="...:drop"` drops a request only while another is in flight, so a repeat sent after the reply needs a service-side guard, such as #49's import token. `server/ui/tests/test_undo_links.py` replays and alters each Undo link a view offers; a new Undo adds its scenario there. A list the page keeps and posts back whole, such as #54's chosen cars, gets a test that makes one item invalid between load and post: #54's vote page kept a car the award could no longer take, and every later vote failed.
- A page that differs from the PHP page it replaces cites a quirk id or an owner decision (`D69`) at the difference, in the code and in any README that describes it, as an endpoint's `divergences` do. #49 and #50 each shipped five such differences with no id until review. `server/ui/tests/test_navigation.py` fails a newly built page until its PHP page is in `ROUTE_DIVERGENCES`, `UNDECIDED_DIVERGENCES` (no id yet; the PR's `## Still open` names each) or `LIKE_PHP` (`server/legacy_api/registry.py`). A difference the ticket's scope asks for is a question for the owner through the lead before the PR, not an `UNDECIDED_DIVERGENCES` entry: #54 parked two there that became D77.
- Each rule lives in its service, and a view or a page's `state.py` calls it. `server/ui/tests/test_rules_in_services.py` flags a lane mask or a service limit copied into one, or a literal bound in its template.
- `server/ui/tests/test_query_growth.py` reads each page, poll and hx-get fragment at two sizes of race day and fails when the query count grows; its first test names a fetched URL missing from `URLS`. Its `race_day()` also feeds `test_poll_signatures.py`, so a feature that adds stored state adds rows in that state there, or both checks pass without rendering it. #70's review found race day with no weigh-in. Race day puts a kiosk on every page in `kiosks.services.kiosk_pages()`, so a kiosk page's thumbnail on the dashboard is counted (#237 retro).
- A new page checks its PHP page's `<script src>` tags: `server/ui/tests/test_php_libraries.py` fails a third-party library the port neither serves nor records as replaced. #52's `fullscreen.php` left out `screenfull.min.js`.
- A setting's bounds and choices are PHP's markup: `server/ui/tests/test_settings_bounds.py` reads them from `settings.php` and `coordinator.php`. A new page with number inputs or `<select>` choices gets the same check.
- `server/tools/source-checks.sh` runs the tests that read only the source (PHP cites and claims, `QUIRK_DECISIONS` records, copied helpers, rules in services, read-then-act, the registry), and the pre-push hook runs it. It took 516 s at a load average of 18 to 27 (#311), about two thirds of it in plan/tests. Run `tools/source-checks.sh --quick` after each batch of edits and before each push. It skips plan/tests and the under-load script's tests and runs on xdist, in about a minute. #48 found five of them failing one round at a time, and #373's hook found a made-up path in a test string, read as a cite, about 15 min into the push. A new test that reads only the source goes into its list: `server/tests/test_source_checks.py` fails a test module that imports `ast` or calls `rglob` and is neither listed nor exempt. #238's fixture-order failure passed the hook because the guard wasn't listed, and only the full suite found it.
- A test of a `plan/bin` or `server/tools` tool calls the tool's function in process where that function takes text (`load_tool()` in `plan/tests/test_affected_tests.py`), and keeps a subprocess or a `git init` for the command line and for git's own behaviour, since the pre-push hook runs these tests on every push. #320's 49 import-only tests each ran `git init` and the tool, 70 s of the file's 205 s at a load of 24; in process, 62 such tests take 6.7 s.
- The page-wide checks fail a new page only once it is registered and renders: `pytest -n auto ui/tests/test_navigation.py ui/tests/test_every_view.py ui/tests/test_query_growth.py ui/tests/test_photo_urls.py` takes about 3 minutes, and `plan/bin/affected-tests` adds them for every template and ui view in the diff (owner, 2026-11-11). Run them as soon as the page has its URL and its registry entry. #52's full suite found four such failures, one round at a time.
- A test for a box that says "X shows what Y shows" compares what each draws: a racer's name, a car number, a label, a value. Checking which template, page name or `data-` attribute X carries proves only that the right template ran. #237's "each of the 15 pages has a thumbnail that matches the page it shows" checked `data-page` and passed while 6 thumbnails were emptier than their kiosks. Review checks this against each such box.
- A browser test reads the page after a click, check or fill through a retrying `expect` (`to_have_css` per card for a CSS order). A one-shot read is kept only where one read is the point, such as "nothing changed", and its comment says so; an experiment showing the read lands late enough is no such reason, and neither is "nothing redraws it", a claim about the page that the Evidence rules cover. #220's sort test kept one-shot reads on that argument and review sent them back; #240's on-deck counts carried `# one read: ... redrawn only when the poll's answer changes`, where `kiosk-ondeck.js:101` redraws at every poll. A box has no retrying `expect`: wait for it with `wait_for_function` (`scaled()` in `test_kiosk_thumbnails.py`). `server/ui/tests/test_browser_one_shot_reads.py` fails a `bounding_box()` with no `# one read:` comment beside it; it leaves `evaluate` to review, since about 30 asserted `evaluate` reads are one read on purpose and #240's carried the mark (#240 retro).
- A contrast or accessibility check starts from `assert_accessible(page)` (axe). A hand-rolled check covers only what axe reports as `incomplete`, and its docstring names that measurement: #247 hand-rolled about 60 lines of WCAG math beside axe, which caught the card regressions and left only text on the kiosk gradient (`bgGradient`) to a check of its own.
- An allowance that drops a browser error (`page_errors.allow`, a `requestfailed` filter) is as narrow as its cause: the frame, the URL and the tests where it happens. A test beside it raises the same error just outside it, such as from the page's own frame, and sees it still fail. #237's first `ABORTED_THUMBNAIL` dropped every `ERR_ABORTED` in two files, the main frame's included. A skip in a check tool, such as `kiosk_screens.py`'s animation rule, is as narrow: it sits in the one check the lead accepted it for, and a stand-in shows every other check still reporting the skipped case. #256 put OVERLAPS's animation skip in the shared `VISIBLE`, so ELLIPSIS missed a name cut in a glowing lane until review. A 404 is allowed only through `page_errors.allow_missing(url_pattern)`, since Chromium's 404 console error names no URL; `ui/tests/test_browser_missing_allowance.py` fails an `allow` that matches it (#206).
- A browser test that claims a step changes nothing records changes while the step runs (a MutationObserver, a call counter) and reads them once, and is checked by mutating every branch past the guard it covers, not only the one it names. #220's held-poll test missed a reload that undid itself before its retrying `expect` gave up; the review's mutation found it. A helper that stops a page's polls is tested with a reply the page handles after the stop, delayed by a Worker timer rather than a fake-clock one: #317's first helper drained, then stopped, and a reply handled late queued its poll again on the resumed clock, which cost a fix round and both 25-count load runs.
- A browser test's wall-clock bound, including a stand-in page's timer raced against a check or a recording's length, writes its slack as a formula in the docstring, gives at least the slack its neighbours give, and carries a should-pass mutation beside the should-fail ones: make the timer late by a bit less than the slack (`setTimeout(..., ms + 150)`) and see the test pass. A review finding or a reply that proposes a timing value goes through the same formula and mutation before it is sent, and a value that misses its stated goal goes to the lead before any long run. #236 held 300 ms, which left 300 ms of slack where the sibling test gives 1000; review then proposed 100 ms, which left 100 ms and failed with the timer 150 ms late. #239's tool test, a clip at 4 s against a 6 s recording, had neither until review. A test that drives a page by hand (`kioskNudge()`, a helper) where the page's own timer would do the same stretches that timer (`TEST_HOOKS` in `test_kiosk_slideshow.py`), and is mutated by removing the hand's call, which must fail it. #253's slideshow test raced the page's 10 s interval, and failed 4 of 4 with it at 5000 ms; four nudge tests in `test_kiosk_pages.py` (now racing, on deck, award, results by racer) pass with `kioskNudge()` running no content poll, since the page's own poll, every 0.5 or 1 s, comes inside `NUDGE_MS` (#253 retro).
- A change the diff makes to a page beyond the ticket's ask, such as a note that moves because a field was added beside it, is fixed in the diff, not listed under `## Still open`. #241's clip note moved under the new ICE servers field, and the fix was one template move.
- A CSS rule's test is mutated by removing the one declaration under test, and its data holds a case only that declaration decides, such as an unbreakable word for `overflow-wrap`. #250's mutations swapped wrap rules for an ellipsis, and removing `overflow-wrap` alone passed, since names with spaces wrap anyway. A fit or overflow check compares the element with its container's box, not with its own `scrollWidth`: in a centred flex column a nowrap name grows past its column. Look at the screenshots before the first mutation round: #250 found mid-word breaks in one after it, and ran the round again. Each condition of a filter is a branch: mutate each operand of an `&&` or `||` to `true` and to `false`, and replace a `min()`, `max()` or `clamp()` by each operand alone (#283's `min(1em, 2.85vw)` kept no mutant with `2.85vw` alone). `server/tools/operand_mutants.py` lists those mutants for each condition and call the diff adds, a Python file's conditions and `and`/`or` operands by its AST, over several lines too, and `server/tools/mutate.py --listed -- <node ids>` runs every one it lists against those tests and prints a row each: the mutation table starts from that run, not from a list picked by hand (#336's 98 picked by hand were mostly one way, and 21 survived on branches no test reached; the listing for `plan/bin/affected-tests` at the same head holds 260). It lists a loop whose body never runs, and a guard in a test file runs once `--file` names that file: #345's scanner loop in `tests/test_docker_checks.py` survived review's `break` mutant. It lists each member of a set literal and of the tuple an `in` tests, taken away: #356's review took `"range"` out of a lookup set and `"values"` out of an `in` tuple, and both survived. The cases it reads past (JavaScript over several lines, a JavaScript ternary, a branch that is no condition, such as a tuple element or a loop's bound) are listed by hand. `server/tools/mutate.py` runs each one against the tests it names by node id, in one process: it refuses a text that does not occur exactly once or a replacement equal to it, a run that deselects a test, runs none or errors with no failure, `-n`, a file that differs from the index (stage the change under test first), and a second run on the file. It restores the file on exit, a SIGTERM, SIGINT, SIGHUP or its `--timeout` included; a SIGKILL leaves the mutant in the file, and the next run refuses it (#319's script ran two mutants on the unmutated tree, and a misspelt `-k` deselected its test without a word). #256's 32 mutations left `playState === 'running' && isFinite(endTime)` with none, and `a => true` passed. Write each near miss's should-fail twin first and see it fail, then the near miss: five of #256's near misses tested nothing until a mutation showed it. A mutation whose result differs from its expected one is explained in the mutation table in the round it runs, or its test or expectation changed: #272's t3 expected a failure, passed on a dead operand, and stood unexplained until review asked. A mutant killed only through the test's own scaffolding, such as a release that rides on the request the mutant removes, counts as survived (#317's M5), and a helper called at two sites gets different data at each, so swapping the arguments fails (#341's timer and replay ages). A guard or hook is also mutated at its call site: delete the call and see a test fail. #282's collection guard took five mutations on its own lines and still passed with its call in `pytest_collection_modifyitems` deleted, until review.
- A browser test that measures text (a width, a line count, a fit) also passes with `DERBYNET_BROWSER_FONT="DejaVu Sans"` before the push, which draws `system-ui` as CI's Ubuntu does, where this machine draws Noto Sans (`server/README.md`). #256, #272 and #273 each held only on Noto, and #273 failed CI on "Heat 100" at 1280x800, which the variable reproduces.
- A condition that names a class of screens, such as TVs and projectors, is tested at its smallest common size too: 1024x768 for a projector. #250's photo cap was tested at 1920x1080 and 1280x800, and shrank a landscape photo at 1024x768 from 176 to 151.6 px.
- A poll that answers 204 signs everything it renders. `server/ui/tests/test_poll_signatures.py` changes each stored field in turn and fails a poll that still answers 204 when its rendering changed. #45's presenter signed the award's key and winner, not the names it shows.

## Evidence

- A claim counts once a test or a real server run reproduces it. That covers a sentence in `GLOSSARY.md`, `plan/owner-decisions.md`, a docstring, a code comment (CSS, JS and templates too), a commit message or the PR body that says what the server, a browser or a library does, and a run count. #237's `kiosk.css` comment said it held every animation at its end, where the rule turns them off; #282's commit message said the run order did not matter, and no run had executed a browser file, then one outside `browser/`, then a browser file. Name the test, the code or the ticket that shows it. A behaviour the diff keeps "as before" names the test that fails when its branch is mutated: #251's body said a columnar place stays blank before the landing, and writing the place on every poll passed every kiosk test until review. Every number, count or comparison in a test's docstring or comments ("8 racers", "58.3 px", "two lines", "among the best") is asserted in that test, or cut, and the PR body lists each one beside the assert that reads it, in a `<details>` block, which review checks against the docstrings: #238's review sent back two that were not, and the second pair of 25-count runs took about 22 min; #272's sent back pixel sizes, a formula and character counts; #273's, briefed with this line, sent back five, three of them words or a default ("two-line", "on 4 lanes" from `race_setup`). `server/tools/docstring_claims.py FILE` prints each number and quoted label in a test file's docstrings and comments, with the code lines that hold its literal, and `--check BODY.md` names each one that no `<details>` line lists beside its test's name, as the tool's table rows do (#324's 2 passed on a 2 in another row): #283's block, written from memory, missed about seven (#283 retro). Run `--check --base` over every test file the diff touches, as `plan/bin/affected-tests` prints it, rather than a catch-all row, which fails: #341 checked two of its four, and review found 28 claims. With `--base` it asks only for the claims of the tests the diff adds or changes and of the tests that read a helper, fixture, constant or import it changes, every module claim once the module's docstring, a module comment or a module-level statement changes, and every claim of a file new on the branch or one it can't resolve (D123, #374): #356 owed 37 rows and #360 owed 75 for tests they never changed. An order claim ("X before Y") gets an assert of that order, and its mutant moves X after Y: #345's Dockerfile comment said the marker is written before the build's `manage.py` calls, and moving it below them passed every test until the advisor asked. A precondition a helper's docstring states, such as "before the page loads", is asserted in the helper, and a test calls it with the precondition broken: #348's `pause_clock_at` stated one unchecked until review, which cost a fix round and a restarted hand-off. A guard and its test are no exception: #282's guard said it names "the first test under here" while its test held one lost test, so a guard that named the last passed, and the test's docstring said "52" errors. When a probe shows a fact a docstring will state, keep the probe as a test first: #224 cited a deleted probe for how Chromium ends an empty 200, and review's finding reran 40 min of load runs. A number measured on PHP is quoted only beside its saved output, a test or a probe and its output named in the PR body: #250 dropped three pixel sizes from a PHP run it had not kept.
- A command a guide or README tells the user to run is a claim too: run it as written, in each shell the text says runs it, and a `docker run` against the image with the variables it shows, before review; the PR body pastes each run's output. #61's guide said PowerShell 7.4 runs the backup with `pwsh` at `/snap/bin/pwsh` unused, and review found `umask` and `<` failing there; its hosted example, never run on the built image, left the container unhealthy (a #58 defect). Output pasted as before or after evidence is a verbatim run of the committed file, whose log names its head; after an edit to the file, run it again rather than note the difference: #345's before banner came from an uncommitted `checks.sh`, and the advisor sent it back. The docs build refuses a fence line it does not take as a fence (`ui/docs/build.py`), and `server/tests/test_guide_commands.py` fails a command of a fenced shell block in `docs/*.md` that has no row in `server/docs/guide-commands.tsv`: a stage of `server/docker/ci/guide-commands.sh` that runs it as written, a live workflow step that holds it, or the reason no check can run it (#414). A guide change adds or changes its rows, and CI runs the stages.
- A comment saying the port does what a PHP page does is a claim too: check it against PHP with `testing/docker/php-scratch.sh`, and `--keep` to measure its page in a browser (#250 retro). #44's playlist back button said "as playlist.php does" and was wrong until #46's retro. Cite the PHP file and line (`kiosks.inc:27-31`) or the test beside the comment; #50's and #52's reviews each sent back comments with neither; `server/tests/test_php_claims.py` now fails an "as X does" or "as PHP's ... does" with neither, in code, Markdown or the port's JavaScript. The PHP run sets up every state the claim covers, or the claim names the states it ran: #247's comment said PHP draws every round's racer white on blue from a run with one round scheduled, and PHP does that only for the running round (`racer-results.css:39-43`, `curgroup`). After each PHP run, reread every PHP claim the diff makes against its output: #252's docstring, written before the cycle probe, said the next drive starts 10 s after the last as PHP's does, and that probe's `cycle-php.json` showed 9.2 s.
