## Spike results: kiosk front end, htmx + Alpine.js vs Svelte

> *This was generated by AI during the spike.* The laptop half of the spike is done. The owner still needs to make the Pi 4 recordings and pick a framework.

**Code:** branch `spike-71-kiosk-frameworks`, directory `prototypes/kiosk-spike/`. The branch is not for merging. It adds nothing under `server/`. A settings overlay (`spike_settings.py`) adds a throwaway `spike` app to the Django skeleton.

**Recommendation: candidate A, Django templates + htmx + Alpine.js.**
- **Smoothness.** A gets its motion from CSS keyframes plus a small FLIP helper built on the Web Animations API. Done that way it drops as few frames as Svelte: 0–2.5% against 0.5–0.7%.
- **Build cost.** A adds no build step and needs no Node. A custom page is a single template.
- **Replay and sync.** Both candidates pass the replay check in the same way. Framework choice has no effect on sync between TVs.
- **View Transitions.** Use them only if the Pi says they are cheap. On this container's software renderer, A with them drops 3–13% of frames. The Pi script records A both with and without them, so the owner can decide per page.

### What was built

Both candidates show the same three pages at 1920x1080. They use one shared stylesheet, so the comparison is about how each animates, not how it looks.

- **Now racing.** The lineup slides in. Results land by place, 400 ms apart, and the winner's lane glows. After a 4 s linger, the next lineup slides in.
- **Standings reveal.** One row per step, from last place up. The new row drops in and the rows below it glide down.
- **Intermission leaders (D55).** Each class's top three takes a turn on a podium, one class every 6 s.

| Poll contracts | now racing: next request 500 ms after each response. Every page: `poll.kiosk` every 5 s | same | same |

**Fixture.** `tools/fixture.sh` builds the data from `create_test_event`, then runs `reset-database.sh`, `import-roster.sh`, `test-den-changes.sh` and `test-master-schedule.sh` against the live Django server, as `server.yml` does. That races every first round through `timer-message`. It then clears the Lions & Tigers results and turns the master schedule off, so that `tools/driver.js` can race fresh heats with `result.delete`, `heat.select` and `timer-message` (HELLO, IDENTIFIED, STARTED, FINISHED). The standings reveal steps through White's Wolves: 13 racers, every heat run. The reveal is driven by `kiosk.assign` parameters `{key, reveal: N | "all"}`.

**Every reveal step animates in all three candidates.** `tools/step-anims.js` counted 18–32 animated frames on each of the 13 steps, with none at zero. Candidate A's later steps run 18–25 frames instead of about 31; those are the dropped frames.

### Animation: frame timing

**The machine.** These numbers come from a 4-vCPU Xeon cloud container with no GPU. Chromium 153 ran headed under Xvfb at 1920x1080 and rasterized and composited in software (SwiftShader). This is not a laptop GPU, and it is not a Pi 4. Treat the ranking as meaningful and the absolute numbers as not. The "4x" rows use DevTools CPU throttling, which slows the main thread but not the software compositor. They are not a Pi emulation either.

**How frames were counted.** `tools/trace.js` records each scenario (about 30 s) with a Chromium performance trace. It counts the trace's `PipelineReporter` frames, which are what the Performance panel's Frames track shows, over the frames flagged as carrying an animation. An in-page `requestAnimationFrame` sampler reports frame intervals over the same run. The sampler adds a main-thread update every frame in both candidates alike.

Raw data is in `results/frames.json`. Recordings are in `recordings/{a,b}-{now-racing,standings,leaders}.webm`. Each is a Playwright video at 1920x1080, 1.9–3.6 MB, taken in a separate run so that encoding did not skew the frame numbers.

What the numbers say:
- **The frame cost in A comes from the View Transitions API, not from htmx or Alpine.** A0 runs the same server, htmx and Alpine with the motion done by CSS and the Web Animations API. It lands level with Svelte. On this software renderer, a view transition snapshots every named element into a texture and composites the snapshots, which is the expensive part. A Pi 4's GPU could make this cheaper or not. Only the owner's Pi traces will tell.
- **One CSS line matters for View Transitions.** Without `:root { view-transition-name: none; }`, the browser cross-fades a full-page snapshot on every step. With the root snapshot on, the standings reveal dropped 56% of its frames (`results/frames-vt-root-snapshot.json`); with it off, 8–12%.
- **Svelte's built-ins worked first time.** In A they needed care. Alpine's `x-show` shows an element one animation frame late, after a view transition or FLIP has already measured the layout, so most reveal steps got no motion until the rows used a bound `hidden` attribute instead. A reveal timer also ran twice until it held its "stepping" flag through the pause between rows.

### Replay iframe check

`tools/replay-check.js` frames each page in `spike/replay-harness`, which reproduces the part of `website/replay.php` the kiosk sees: `#interior` iframe, `announce_to_interior()`, `postMessage(msg, '*')`. The check cuts to a replay part-way through an animation. While the replay shows, the timer reports another heat, or a reveal step falls due. Then the replay ends. Everything was automated with Playwright.

| Page | Candidate | Animations paused | Clock moved while paused | Polls while paused | Steps while paused | After `replay-ended` | Pass |
|---|---|---|---|---|---|---|---|
| Now racing | A / A0 / B | 9 / 9 / 9 | 0 ms | 0 / 0 / 0 | none | the paused results finish. Then, after the 4 s linger now-racing.js keeps, the next lineup: 4.5 / 4.8 / 4.4 s | yes / yes / yes |
| Standings | A / A0 / B | 6 / 2 / 2 | 0 ms | 1 poll.kiosk each (kiosk-poller.js never suspends) | none | next row in 1.9 / 1.8 / 0.0 s | yes / yes / yes |
| Leaders | A / A0 / B | 6 / 4 / 4 | 0 ms | 0 | none | next panel in 0.1 / 0.5 / 0.0 s | yes / yes / yes |

Raw data is in `results/replay.json`.

**Both candidates handle the replay the same way.** `spike/static/spike/spike-common.js`, 15 lines of plain JavaScript, is shared by every page. On `replay-started` it calls `document.getAnimations().forEach(a => a.pause())`, which covers CSS animations, view transitions and Svelte's Web Animations alike, and it tells the page to stop polling and stepping. `replay-ended` reverses both.

**One requirement for the rebuilt pages.** The skeleton's `XFrameOptionsMiddleware` answers `X-Frame-Options: DENY`. `/health/` and `action.php` both return that header. A DENY view framed in the harness shows Chromium's error page (`chrome-error://chromewebdata/`, checked with Playwright). Each kiosk view needs `@xframe_options_sameorigin`, as the spike's views have.

### Polling and push: how far apart two TVs are

`tools/sync.js` opens two browser instances, standing in for two TVs, at random moments so that their poll cycles are out of phase. It drives the steps through the legacy API and reads, on one clock, when each instance started each step's animation. Raw data is in `results/sync.json` and `results/sync-nr-debug*.json`.

| Mode | Page | Expected skew (independent poll phases) | Measured skew, A | Measured skew, B | Latency to animation start |
|---|---|---|---|---|---|
| Polling | Now racing (`poll` 500 ms after each response, about a 515 ms cycle) | uniform phase gap; mean ≈ 170 ms, max ≈ 515 ms | 239–276 ms (a pair whose phases stayed apart) | 239–272 ms | 0.2–0.5 s |
| Polling | Standings step (`poll.kiosk` every 5 s) | mean ≈ 1.7 s, max 5 s | 2.40 s on every step (fixed phase gap) | 0.14 s on every step | 2.0–3.4 s mean, up to 4.0 s |
| Push (SSE notice, then the same fetch) | Now racing | — | mean 8 ms, max 12 ms | mean 9 ms, max 19 ms | 61 / 43 ms mean |
| Push | Standings step | — | mean 8 ms, max 51 ms | mean 8 ms, max 51 ms | 41 / 36 ms mean |

- **Polling cannot keep the TVs in step.** The skew between two TVs is however far apart their poll cycles happen to be. For `poll.kiosk`, that is anywhere from 0 to 5 s, fixed for as long as both TVs stay up.
- **A caveat on the now-racing polling numbers.** In the full run, both pairs measured only 10–30 ms apart. That is not something polling can be relied on for. The two poll chains drifted into lock-step during the heats: on `runserver` both requests are handled in one Python process, so requests that overlap finish together. That is the likely cause, but it is unverified. A pair kept apart reproduced the expected skew of about 250 ms.
- **Push makes the framework irrelevant.** Both candidates start within 8 ms of each other on average, and within 51 ms at worst. The 36–61 ms latency includes the spike stream's 50 ms database check. A notice sent by the write itself would be faster.
- **Request load.** In about 65 s, one now-racing TV sent 129–135 polls with polling and 20–21 with push, where the chain fell back to 5 s.

The push finding is posted to #56 separately (`PUSH-FINDING.md`).

### What starting an animation from a push notice needs

- **A:** load the 2.9 KB htmx SSE extension (`htmx-ext-sse`). Put `sse-connect="/events"` on the page and add `sse:change` to the element's existing `hx-trigger`. That is no JavaScript. The notice runs the same fragment request as a poll, and the animation follows from the swap.
- **B:** one line, `new EventSource('/events').addEventListener('change', poll)`, calling the same function the poll chain calls.
- **Both:** keep the poll chain as the fallback, at a slower rate. On the server, each TV holds one streaming connection. `runserver` gives each connection a thread; #58's gunicorn sync workers cannot hold such connections, which is #56's decision (ASGI, threads or gevent, and `proxy_buffering off` in nginx).

### Custom page

Sketches, not wired up, are in `custom-page-sketch/`.

- **A (`a/fastest.html`):** the owner writes one Django template, a "fastest five" board. It receives its data from the same services the built-in pages use, gets its motion from CSS classes or a `<style>` block, and refreshes with `hx-trigger="every 5s, kiosk:changed"`. Edit the file and reload the browser: no build, no Node. Mistakes surface as template errors on the server.
- **B (`b/Fastest.svelte`):** the owner writes one Svelte component with `animate:flip` and `in:fly` from the library, plus a JSON endpoint on the server. Every change needs `npm run build` on a machine with Node, or a new image (#58), because the server has no Node at runtime.

### Why A, with the numbers

1. **Smoothness:** A0 drops 0–2.5% of frames and B 0.5–0.7% at 1x; at 4x, 1.1–2.1% against 1.5–4.5%. The difference between the frameworks is noise. A's View Transitions add 2–10 points of dropped frames on this renderer.
2. **Build cost:** A adds no Docker build stage and no Node. B adds a Node stage, 39 npm packages and a lockfile, beside the htmx, Alpine.js and Tailwind stack that ADR-09 already uses for the manager UI.
3. **Replay:** both pass with the same 15 lines.
4. **Sync:** depends on push, not on the framework. With push, both are within 8 ms on average.
5. **Custom page:** A is one template the owner can edit live. B needs a rebuild.
6. **What A costs instead:** there is no built-in FLIP or enter and leave transitions, so A needs a small shared helper library of about 50 lines for FLIP, the replay pause and the poll chain. Its authors must know traps such as Alpine's late `x-show`. Svelte gives these for free, and its components are a little shorter.

**Suggested shape for #52 and #46:**
- Use CSS keyframes for elements that enter.
- Use a shared `flip()` helper (Web Animations API) for rows that move.
- Use View Transitions only for whole-board swaps, and only if the Pi traces show them cheap, always with `:root { view-transition-name: none; }`.
- Every page gets the shared replay handshake.

### Not possible here

- **Pi 4 recordings and dropped-frame numbers.** These are the owner's. `pi/record-kiosk-spike.sh http://LAPTOP:8771` opens each candidate and page (a, a0, b × 3 pages) full screen in Chromium with the flags `extras/scripts/kiosk.sh` uses, and drives the same scenarios with curl. It writes, per run, a Chromium trace (`--trace-startup`, no DevTools needed) and a second-pass screen recording: `wf-recorder` on Wayland, `ffmpeg` x11grab on X11. It then prints the dropped-frame table with `pi/summarize-trace.py`. The script was tested here only with Playwright's Chromium under Xvfb, not on a Pi; that run needed `CHROMIUM_EXTRA_ARGS=--no-sandbox` because it ran as root. A trial run of the standings page for A0 and B wrote both traces and both x11grab recordings, and printed the table (A0 0.2% dropped, B 0.0%).
- **A real laptop GPU.** The container renders in software, so the absolute frame numbers will be better on real hardware. The A-versus-A0 View Transitions gap may shrink there.
- **Older kiosk browsers.** Not tested: `kiosk.sh` can also run Midori or Epiphany. Without View Transitions support, A falls back to an instant swap. B and A0 need only the Web Animations API.
- **Push under the production server.** The SSE stream ran under `runserver`. Its behaviour under gunicorn, ASGI and nginx is #56's to measure.

prototypes/kiosk-spike/serve.sh 8771                          # Django skeleton + spike app, SQLite in var/
prototypes/kiosk-spike/tools/run-all.sh http://127.0.0.1:8771 # fixture, frames, replay, recordings, sync, loc (about 40 min)

The Svelte bundle in `svelte/dist/` is committed, so running needs no Node. To rebuild it: `cd prototypes/kiosk-spike/svelte && npm ci && npm run build`.
